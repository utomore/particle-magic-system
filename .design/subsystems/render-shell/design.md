# 渲染外殼 子系統架構

## 定位與範圍

承接 [system.md](../../system.md)「子系統劃分 → render-shell」。六塊裡唯一**不純**的一塊：整個專案所有的 IO——開視窗、讀時鐘、讀檔案、呼叫圖形硬體——都在這裡，其餘五塊加起來一行 IO 都沒有。

它同時是一個**證明**：這一塊整組刪掉，庫還是完整的。它消費 [boundary-host](../boundary-host/design.md) 的輸出，反過來沒有任何庫元件依賴它——由套件結構強制。**demo 是庫的第一個宿主，不是庫的一部分。**

**做**：固定時步主迴圈與視角狀態、魔法陣檔案的熱重載與清單熱掃描、3D 與 2D 後端、批次幾何建構、深度排序與跨批交錯、自訂著色器與後處理、HUD 與即時參數面板。

**明確不做**：

- **不定義任何對外合約**。這裡的每一個型別都可以明天換掉。
- **不含魔法語意**。參數面板要改一個參數，走的是「改魔法陣的正規序列化形式再重新載入」——因為這一層**看不到魔法陣的內部結構**。這不是繞路，是邊界正在生效的證據。
- **不把繪圖概念推回庫裡**。鬆綁的是「外殼能不能用自訂著色器」，不是「渲染細節能不能進庫」。玩家在資料檔裡寫著色器程式是**永久非目標**。

## 對外契約（Public Interface & DTOs）

**本子系統沒有對外程式介面**——它是終端消費者，沒有任何元件依賴它。它的「契約」是兩個方向：

### C1 往內消費（唯一的一條路）

只准經 boundary-host 的入口取用：法術生命週期、編解碼、投影、時步規劃。**構不到核心內部**，由套件結構強制。

### C2 呈現面（對操作者的契約）

demo 執行檔與其操作方式：切換法術、切換視角（3D 軌道／2D 側視／2D 俯視）、相機操控、四項產品級特效各自一個開關、開關參數面板、熱重載回饋與錯誤上屏。

**這些是呈現選擇，明文不凍結。** 螢幕映射的原點與縮放比例屬於外殼的呈現決定，不是對外介面——需求真的出現時再考慮提升，而不是預先凍結。

### C3 零漣漪律（本子系統最重要的一條自我約束）

每一項視覺增強都要能單獨關掉，且**全關時的輸出與該功能不存在時逐位元相同**。四項產品級特效各自一個按鍵、預設全關，正是這條律的兌現。

## 內部模組劃分（Internal Modules）

分三群：**效果定義與純決策**、**渲染管線（全純）**、**IO 解譯器**。

| 模組 | 群 | 單一職責 |
|---|---|---|
| **M1 效果定義與詞彙** | 定義 | 三個效果（時鐘、檔案監看、圖形）的**定義**，不含解譯器；相機、視角模式、HUD 與面板的觀測詞彙、輸入詞彙。**渲染器無關** |
| **M2 主迴圈與視角** | 決策 | 固定時步驅動、視角狀態的純轉移、法術清單合併、呈現常數 |
| **M3 熱重載** | 決策＋IO | 純決策（何時該重載、重載哪些）與 IO 輪詢分開匯出 |
| **M4 渲染管線** | 純計算 | 批次幾何建構（含速度拉伸與多形狀合併）、深度排序與跨批交錯、上傳分塊、程序生成貼圖與圖集、後處理的**通道計畫** |
| **M5 IO 解譯器** | IO | 圖形效果的兩個解譯器：真實後端（**唯一碰渲染函式庫的地方**）與 headless 後端 |
| **M6 2D 後端與螢幕映射** | 純計算＋IO | 正交視圖的幾何建構、平移縮放與視窗適配 |
| **M7 觀測與互動面** | 決策 | HUD 文字格式化與幀率平滑、參數面板的純狀態機與寫回、軟粒子驗證用的最小場景幾何 |

**本子系統最重要的內部紀律：純計畫與 IO 執行分離。** 後處理通道計畫、幾何建構、排序、面板狀態機、HUD 文字全是純函數，IO 解譯器只負責照著計畫呼叫。結果是三十份以上針對本子系統的測試**一份都不需要開視窗**。

## 資料流管線（Data Flow Pipeline）

```text
輸入      時鐘（經過時間）／檔案系統（魔法陣檔）／鍵盤滑鼠
  │
驗證      M3 純決策：時間戳變了嗎、清單變了嗎
          載入失敗 → 錯誤字串上屏，不中斷迴圈
  │
業務處理  M2 依固定時步規劃推進 → 呼叫 boundary-host 取得渲染批次
          M2 視角輸入的純轉移
          M4／M6 把批次變成幾何：
             排序 → 建構四邊形（或速度拉伸／多形狀合併）
             → 分塊 → 後處理通道計畫
          M7 HUD 文字、面板狀態機
  │
儲存      參數面板的寫回：改魔法陣的正規序列化形式 → 落檔 → 觸發熱重載
          （這一層看不到魔法陣的內部結構，所以只能走這條路）
  │
輸出      M5 解譯器照計畫執行：上傳、繪製、後處理鏈、呈現
          或（測試時）headless 解譯器記錄呼叫而不繪製
```

## 模組間公開介面（Module Interfaces）

| # | 呼叫方向 | 契約內容 |
|---|---|---|
| **I1** | M2／M3／M7 → M1 | 一切跨模組的觀測與輸入都以 M1 的渲染器無關詞彙表達，**不直接使用渲染函式庫的型別** |
| **I2** | M5 → M1 | 解譯器實作 M1 定義的效果；同一組效果有真實與 headless 兩個實作，因此測試不需要視窗 |
| **I3** | M2 → M4／M6 | 主迴圈把渲染批次交給管線，取回**純資料**的幾何與通道計畫 |
| **I4** | M4 內部 | 後處理的通道計畫先算出需要幾張暫存目標，**分配之前就知道要幾張** |
| **I5** | M7 → boundary-host | 參數面板經編解碼往返修改魔法陣，不經過任何核心型別 |
| **I6** | M3 → M2 | 熱重載的決策結果餵給主迴圈；IO 半邊由 M1 的效果解譯 |

## 使用的技術

| 選型 | 理由 |
|---|---|
| **圖形函式庫（含 C 原始碼）** | 主架構既定。首次建置需可用的 C 工具鏈且耗時長，是整個技術棧風險最高的一點，已在骨架階段最先驗證 |
| **動態四邊形網格** | 逐實例繪製經實證否決（綁定無逐實例顏色且需自訂著色器）。改走每批一次繪製，**繪製呼叫數＝批次數而非粒子數** |
| **效果系統** | 三個效果各有真實與 headless 兩個解譯器；配對呼叫以資源獲取模式封裝 |
| **自訂著色器** | 取代了「不自訂著色器」的舊前提。軟粒子要取樣深度、光暈要亮度萃取與模糊，兩者都無法用預設管線做。**繪製路徑保留不變** |
| **貼圖圖集做跨批交錯** | 「每批一個置換」無法兌現全域順序（批次仍連續繪製）。改以圖集讓全體同混合模式的粒子進同一次繪製；副作用是繪製呼叫反而更少 |
| **輪詢而非檔案系統事件** | 既定延後並再次確認：十來個檔案的規模輪詢零成本 |

- **資料流管線段落**：輸出段——低解析目標與放大
- **驗收標準**：食譜裡寫的兩件事（低解析目標整數倍放大、調色盤量化）真的有一個可執行的示範走過；像素對齊沒有接縫或抖動
- **明確不做**：不把螢幕映射提升為對外介面；不改變 2D 投影的語意

### order-introsort

- **階段**：階段五（候選）
- **負責模組**：M4 渲染管線
- **實作的 Level 2 介面**：無新增，優化 C1 消費 boundary-host 排序後的內部路徑
- **資料流管線段落**：業務處理段的排序
- **驗收標準**：排序改為原地演算法後，繪製順序**逐位元不變**（仍是穩定置換），且有前後對照的耗時數字
- **明確不做**：不改變排序的語意或穩定性；在未量到熱點前不動手
