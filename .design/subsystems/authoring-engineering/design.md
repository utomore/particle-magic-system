# 作者工具與工程化 子系統架構

## 定位與範圍

承接 [system.md](../../system.md)「子系統劃分 → authoring-engineering」。六塊裡唯一**不在三環裡**的一塊。它的產物一行都不進出貨的庫，也不影響任何執行期行為——但沒有它，另外五塊沒辦法被別人使用、也沒辦法被安全地發布。

服務兩種人：**寫魔法陣的人**（要知道格式、要在存檔前就知道寫錯了、要看得到這張陣加起來是什麼）與**發布這個庫的人**（要知道哪些平台驗過、版本怎麼跳、哪些東西凍結了）。

**做**：三支命令列工具、作者面與宿主面文件、機器可讀的格式宣告、文件↔程式碼的守門測試、CI 矩陣與發布政策。

**明確不做**：

- **不進庫**。三支工具都是獨立執行檔；其中產生格式宣告的那支**完全不依賴這個庫**——這正是它能當 golden 比對而不是「第二意見」的原因。
- **不做視覺化編輯器**。等有非工程作者為止。demo 內的參數面板是這個方向的雛形，不是替代品。
- **不上公開套件庫**。已裁決。

## 對外契約（Public Interface & DTOs）

### C1 命令列契約

| 條目 | 契約 |
|---|---|
| **C1.1 驗證工具** | 吃一個檔案或目錄，載入並施放每一份魔法陣，回報成功或失敗；支援機器可讀輸出。**退出碼有語意**：全數通過與有失敗必須可區分 |
| **C1.2 檢視工具** | 吃一個檔案，輸出「這張陣加起來是什麼」的人類可讀報告。**每個數字都來自既有的邊界層查詢**——工具不做自己的分析，只把答案排版 |
| **C1.3 格式宣告工具** | 印出或**比對**機器可讀的格式宣告；比對不符即以失敗退出 |

兩支施法的工具共用同一份施法上下文與生命週期取得方式——兩者報告的是同一次施法，保證這件事的方式是**只有一份定義**。

### C2 格式宣告（機器可讀）

一份可被編輯器與 CI 消費的格式宣告檔，涵蓋魔法陣的所有鍵與值域。**權威在檔案本身**，由 C1.3 的比對守護。

### C3 文字合約（本子系統的核心機制）

模式一律相同：**程式碼裡有事實，文件裡有敘述，測試斷言兩者相等。**

| 條目 | 釘住的兩端 |
|---|---|
| **C3.1 格式文件** | 出貨範例用到的每個鍵都必須出現在作者手冊 |
| **C3.2 三方一致** | 格式宣告檔 ↔ 產生器 ↔ 作者手冊 |
| **C3.3 平台清單** | 發布政策 ↔ 相容性決策 ↔ CI 矩陣，三處相同 |
| **C3.4 版本後設** | 套件版本與測試過的編譯器版本 ↔ 變更記錄 ↔ 發布政策 |
| **C3.5 CI 設定** | 觸發條件與矩陣本身 |
| **C3.6 範例與綁定** | 範例宿主的每個檔案都列進出貨清單；參考綁定 ↔ 凍結的 C 標頭 |

**這招的已知盲區**：對「IO 端產生、純端比較相等」的東西無效——曾有一次平台路徑差異讓兩者不相等，程式照跑、只有畫面看得出來。結論寫成一條紀律：這一類地方都要有一條**打真實檔案系統**的守護測試，外加一次人眼確認。

### C4 發布契約

平台分級、版本上界規則、版本標籤格式，以及「C ABI 世代與套件版本各自獨立遞增」。

## 內部模組劃分（Internal Modules）

| 模組 | 單一職責 |
|---|---|
| **M1 驗證工具** | 命令列剖析、逐檔載入與施法、人類與機器兩種報告、退出碼判定；持有兩支工具共用的施法上下文定義 |
| **M2 檢視工具** | 法術報告的排版；不做分析，只呼叫邊界層查詢 |
| **M3 格式宣告工具** | 手寫的宣告表、比對模式，以及一個**自帶的**格式驗證器子集 |
| **M4 作者面與宿主面文件** | 格式手冊、宿主整合指南 |
| **M5 發布政策與版本後設** | 發布流程、變更記錄、套件後設資料 |
| **M6 CI** | 兩平台矩陣的建置、測試與驗證流程 |
| **M7 文字合約守門測試** | C3 的六條 |

**依賴紀律**：M1 與 M2 依賴邊界層，**構不到核心、也構不到任何渲染器**。M3 更嚴——**不依賴這個庫的任何部分**。

## 資料流管線（Data Flow Pipeline）

```text
作者路徑
  輸入    一份（或一整個目錄的）魔法陣檔
    │
  驗證    M1 載入 → 邊界層解碼（文法、值域、算式）
          失敗 → 帶位置的錯誤，計入失敗數
    │
  處理    M1 施法 → 取得預算、生命週期、發射器
          M2 以同一份上下文再問一次，排版成報告
    │
  輸出    人類可讀報告 ／ 機器可讀報告 ／ 退出碼

發布路徑
  輸入    一個提交（或一個版本標籤）
    │
  驗證    M6 在兩個平台上建置 → 跑測試 → 跑驗證工具
          M7 的六條文字合約在測試中一併執行
    │
  輸出    綠燈或紅燈；版本標籤觸發時再驗一次

格式路徑
  M3 手寫宣告表 ──產生──▶ 宣告檔
                  ╲比對╱
                   已提交的宣告檔  ← C1.3 的 golden 比對
```

## 模組間公開介面（Module Interfaces）

| # | 呼叫方向 | 契約內容 |
|---|---|---|
| **I1** | M2 → M1 | 檢視工具沿用驗證工具定義的施法上下文與生命週期取得方式，**只有一份定義** |
| **I2** | M1／M2 → boundary-host | 只用既有的公開查詢；工具不新增任何分析 |
| **I3** | M7 → M3／M4／M5／M6 | 守門測試讀文件與設定檔的**原文**，與程式碼裡的事實比對 |
| **I4** | M3 內部 | 宣告表是**手寫**的，不從型別反射產生——若自動導出，它與編解碼會同時對或同時錯，比對就只是重算而非驗證 |

## 使用的技術

| 選型 | 理由 |
|---|---|
| **手寫的宣告表** | 見 I4。這是本子系統最重要的一個設計決定 |
| **自帶的格式驗證器子集** | 不引入格式驗證的執行期依賴；明列支援範圍，超出即報錯而非默默略過 |
| **兩平台 CI 矩陣** | 閘門設在**併入主線**而非日常推送——私有倉庫計費，且其中一個平台的執行器成本是兩倍 |
| **版本上界** | 兩個公開 sublibrary 對外，破壞凍結介面等於主版本跳號 |
| **換行正規化** | 必需品而非細節：工作樹的換行風格會讓「產生物 vs 已提交檔案」的比對假性失敗 |

**一個由 CI 買來的發現**：第一次在非原生開發平台上跑整套測試時，二十多條逐位元 golden 變紅，根因是數學函式庫的三角函數不保證正確捨入，輸出端絕對差極小。決定論的宣稱因此從「每個平台」收窄為「同平台逐位元、跨平台結構＋容差」。**這是「只有一個平台實測過」的真正代價，而它只有跑過才看得見。**

## 開發階段

不屬於主架構的任何一條核心開發鏈——它與所有子系統零檔案交集，因此**任何時候都能插隊平行推進**，這也是它三次都能與別的工作同時進行的原因。對應主架構 P4。內部里程碑三個，皆已達成：作者回饋圈 → 工程化 → 機器可讀。

## Feature 契約卡

### llvm-backend-eval

- **階段**：階段四（候選）
- **負責模組**：M6 CI
- **實作的 Level 2 介面**：無新增，擴充 C3.5 CI 設定
- **資料流管線段落**：發布路徑的建置段
- **驗收標準**：以替代編譯後端建置並跑完整套測試，得出「值不值得」的量測結論與建置時間代價；**不論結論如何，輸出必須逐位元不變**，否則決定論宣稱要跟著改
- **明確不做**：不為此改任何程式碼；不在沒有量測的情況下切換預設

### schema-v2-tooling

- **階段**：階段四（候選）
- **負責模組**：M3 格式宣告工具、M4 文件、M7 守門測試
- **實作的 Level 2 介面**：擴充 C2 格式宣告（多版本）與 C3.2 三方一致（每版一組）
- **資料流管線段落**：格式路徑全段
- **驗收標準**：兩個格式版本各有宣告檔、各有 golden、各有手冊章節，且三方一致的守門對每一版都成立；舊版檔案仍能被驗證工具接受
- **明確不做**：不定義遷移的語意（那在 boundary-host 的編解碼）；不在版本真的遞增前先做

### visual-editor

- **階段**：階段四（候選）
- **負責模組**：M1 驗證工具、M2 檢視工具
- **實作的 Level 2 介面**：新增一條互動式的編輯與預覽契約，建立在 C1.1／C1.2 之上
- **資料流管線段落**：作者路徑——把「編輯 → 驗證 → 看結果」縮成一個迴圈
- **驗收標準**：非工程背景的作者能在不讀格式手冊的情況下組出一張可用的魔法陣並看到結果
