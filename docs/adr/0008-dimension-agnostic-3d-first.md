# ADR-0008：維度無關核心，3D 優先投影

- 狀態：已採納（2026-08-11）
- 相關：[architecture.md §1.5, §5.2](../architecture.md)

## 背景

系統設計目標要求「未來此系統要能夠在任何其他形式的遊戲都可以運行，2D、3D 都可以。本質不變只是投影映射到 2D、3D 空間」。同時 POC 需要選定第一個實際渲染目標。

## 決策

1. **核心在抽象 3D 空間運作**：所有粒子位置、法線、形狀取樣都是 `V3`；系統輸出 `RenderBatch` 不含任何維度或渲染後端的假設（也不含任何 raylib 型別）。
2. **投影是外殼層的職責**：`Magic.Project` 提供投影抽象，3D 透視是自然情形，2D 是正交投影（丟棄一軸＋深度排序策略）的特例。
3. **POC 的第一個展示層是 raylib 3D**（`App.Render.Raylib3D`）。

## 後果

**正面**：
- Init.md 的核心流程「一個點與法線 → 初始面 → 往法線方向擴充立體」只有在 3D 下才能被完整驗證；3D 優先直接打擊風險最高的語意。
- 「本質不變、只換投影」從口號變成型別事實：`FrameOutput` 與維度無關，宿主換 2D 遊戲時核心零改動。
- 2D 支援的成本被精確地圈在一個模組（投影函數＋外殼後端）。

**負面**：
- 3D 展示層的除錯比 2D 難（攝影機、深度、透視），POC 初期迭代較慢。
- 2D 的視覺可讀性問題（立體擴充在正交投影下的重疊）被延後發現——已列入 architecture.md §8 的已知風險。
- 純 2D 遊戲宿主要為用不到的第三軸付出少量記憶體與運算成本（一條 `U.Vector Float`）；量級上可忽略。

## 被否決的替代方案

- **2D 優先**：渲染與除錯簡單、迭代快，但「沿法線擴充立體」的核心概念只能被間接驗證，且展示層先做 2D 容易讓 2D 假設滲入介面設計，之後轉 3D 反而返工。
- **兩者並行**：最能證明維度無關的目標，但 POC 工作量近乎翻倍；維度無關性已由「輸出型別不含維度假設」在架構層保證，不需要用雙倍實作來證明。
- **核心參數化維度（`V n` 泛化向量）**：型別上優雅，但為了 2D/3D 兩個具體情形引入型別層自然數與泛化線性代數，複雜度不成比例；固定 `V3`＋投影足以覆蓋需求。
