# ADR-0014：符文陣由魔法陣資料導出——摘要即合約、混合導出、逐位元豁免的邊界

- 狀態：已採納（2026-08-15）；**D5 已由 [ADR-0015](adr-0015-sigil-persists-through-cast.md) D4 取代（2026-08-15）**——陣形改為駐留到 `ppEnd`，D5「豁免只到 Drawing／Converging 為止」的前提（陣形於 `castStart` 死盡）不再成立。本文其餘決策不受影響。
- 相關：[architecture.md §1.1（Circle as Data）、§3.3（生命週期）、§4.3（`hashChan`）、§11（破壞性變更硬點表）](../architecture.md)；ADR-0003（槽位固定職責）、ADR-0007（核心零 IO）、ADR-0010 D4／D9（力場是陣的物理環境、零場逐位元相容律）；落地 spec：0016

## 背景

架構書 §1.1 說魔法陣**是資料**，解釋器讀它、玩家組合它。但 0016 之前，這句話只兌現了一半：資料決定粒子**怎麼飛**，卻不決定陣**長什麼樣**——畫陣階段一律是六層同心環帶加四個節點，而且環帶是面積均勻亂數散佈（`sampleShape` 的環＝在圓環面積裡撒點），所以畫出來的不是線，是霧。任何魔法陣看起來都一樣。

要讓陣成為「這個魔法自己的陣」，必須回答三個結構問題：

1. **幾何從哪裡來？** 讓玩家直接指定？由資料導出？導出的話，導出多少？
2. **導出函數能不能改？** 玩家會以外觀辨識法術，那麼決定外觀的函數是不是合約？
3. **既有法術的逐位元相容承諾怎麼辦？** 0007／0010／0012 都建立在「既有範例逐位元不變」的網子上。

## 決策

**D1（陣形幾何由 `Circle` 導出，不開放直接控制）** 陣是魔法的**指紋**，不是作者資料。玩家寫的每一個符文都會改變陣的長相，而陣的長相沒有獨立的作者欄位。理由有三：對應關係一旦可被繞過（作者可以畫一個與內容無關的陣），「看陣就知道是什麼魔法」這條遊戲層的可讀性就沒了；直接控制需要 schema 升版與一整套幾何 DSL；而導出版本**零 JSON 鍵**——schema 一字不動就得到全新的視覺維度。開放作者控制留待遊戲層真的需要「自訂徽記」時再談，屆時是新的鍵，不是改這一條。

**D2（混合導出：結構定骨架、摘要定花紋）** 層數與半徑帶來自**佔用了哪些槽位**（結構），對稱階以佔用數為中心、由摘要在 ±1 內取值，而每層用哪種筆畫、起始相位、各筆畫參數來自**結構摘要**（`hashCircle`）。

被否決的是**全摘要**方案（連層數都由 hash 決定）：它變化最大、實作最簡單，但陣的外觀與魔法內容失去可讀的對應關係——「這個陣有五圈是因為它佔了五個槽」這件事看不出來了——而且改一個小參數整個陣就面目全非。混合方案讓結構性的東西看得出來，同時每個法術的細節仍然獨一無二。

**D3（摘要即合約：`hashCircle` 交付即凍結）** 玩家以外觀辨識法術，所以改摘要函數＝**靜默改變每一個法術的長相**。這與 architecture §11 的「`Expr` 語意變更」同一級別，必須併入 §11 的硬點表。三條實作後果：

- 浮點以**位元**（`castFloatToWord32` / `castDoubleToWord64`）進入摘要，不走十進位近似——否則同一份 JSON 在不同平台可能算出不同的陣；
- 摘要沿用 `hashChan` 的 splitmix64 常數與混合形狀，專案只有一套雜湊算術；
- `emptyCircle` 的摘要值寫成測試裡的哨兵（`11072995449257717738`），任何無意的改動都會撞上它。

**D4（力場不進摘要）** `circleFields` 刻意**不**折進 `hashCircle`。ADR-0010 D4 已經裁定力場是陣的**物理環境**，既不是任何槽位的意義、也不是對意義的調變；ADR-0010 D9 則交付了「零場逐位元相容律」與「力場不改變解釋器其他產物」。若把力場折進摘要，掛一個重力井就會靜默重畫整個陣——那是對 D9 的可見違反。所以力場一如它穿過 `compile` 的方式：被攜帶，不被折疊。

**D5（逐位元豁免只到 Drawing／Converging 為止）** ⚠ **已由 ADR-0015 D4 取代**——邊界收窄為 `t < min(phDraw, castStart − formLife)`，理由見該處。以下保留原文作為記錄。

本輪改變的是畫陣階段的幾何，因此：

- `circlePhases = Nothing` 的法術**完全不受影響**（它們根本沒有陣形發射器）——0010 的 golden 網對這 8 個範例零重錄；
- 有 `phases` 的法術，只有 `t < castStart` 的畫面改變；`t ≥ castStart` 起，緩衝區就是施放發射器自己的，逐位元不變。實測驗證：`bare-sigil` 240 幀中差異落在幀 0–89（castStart = 1.5 s ＝幀 90），`grand-sigil` 落在幀 0–106（castStart = 1.8 s ＝幀 107），此後每一幀逐位元相同。

豁免的**代價**照付：`test/golden/perf-0010/{bare,grand}-sigil.txt` 與 `FieldPlumbingSpec` 的兩個摘要重錄，並在該處註明理由。豁免的**邊界**由 `SigilWiringSpec` 的結構性斷言守著（「從 castStart 起，有相位的法術取樣結果恰等於只留施放發射器的同一法術」），而不是靠重錄後的數字自我證明。

**D6（一筆畫一個發射器）** `SigilPlan` 的每個 `SigilStroke` 編成一個 `EmitterSpec`。預算逐筆結算（0010 的 `ParticleBudget` 自動涵蓋）、時間窗剔除逐筆生效（`aliveRanges`）、0015 的分批逐筆分組——因此 `sampleStroke` 內**不需要**前綴和或分派，取樣維持 O(1) 無配置。代價是發射器數由 ~11 升至 ~20，而 0010 §9.2 量到的 per-emitter 成本是每幀一次基底提升，可忽略。

`SigilPlan` 本身是 `compile` 期的中間值，不進 `CompiledSpell`；只有單筆 `SigilStroke`（6 個 strict 欄位）隨 `SpawnOnStroke` 進入 `Motion`，與 `FaceShape` 同性質。**無新的跨幀狀態**——系統唯一的跨幀狀態仍是 0007 的 `FieldState`。

**D7（符文帶的字不表義）** `GlyphBand` 是 3×3 點陣上 12 條候選線段的位元遮罩。這些「字」是**紋樣，不是文字**：不對應任何字母表、不表義、不是字型。真正的符文語言（字符集、拼寫規則、字義影響魔法）是遊戲層的設計，屆時是新的資料與新的 spec，不是把意義追認給這 12 個位元。

## 被否決的方案

- **玩家直接指定陣形幾何**——見 D1；破壞「陣＝魔法的外觀」的對應關係，且需 schema 升版。
- **全摘要導出（層數也由 hash 決定）**——見 D2；變化最大但失去可讀性。
- **摘要函數保留調整空間（不凍結）**——見 D3；等於保留「隨時靜默重畫所有法術」的權利。
- **力場折進摘要**——見 D4；直接違反 ADR-0010 D9。
- **在 `sampleStroke` 內以前綴和分派多筆畫到單一發射器**——見 D6；省下的發射器數遠不及失去的逐筆預算與剔除。
- **保留 0006 的環帶取樣、只加筆畫作為額外層**——霧仍然是霧，再多層也不會變成線；而且預算會翻倍。

## 後果

**正面**：
- architecture §1.1 第一次**看得見**：同一份 `Circle` 永遠畫出同一個符文陣，不同的 `Circle` 畫出看得出差異的陣（三個範例陣目視確認，見 func-spec 0016 §9）。
- 「索引序＝繪製序」讓陣是**被畫出來**的，而這條律**零新機制**——它直接來自 0002 就凍結的 `firstBirth`。畫陣階段的語意本來就是這個，0016 之前只是把它浪費掉了。
- `Magic.Codec` 零觸碰、schema 不升版、不加任何符文：全新的視覺維度，作者面零成本。
- 力場、施放階段、無相位法術全數不受影響，0007／0010／0012 的相容網完好。

**負面／記帳**：
- `hashCircle` 成為與 `Expr` 語意同級的凍結物，架構書 §11 硬點表需增列一行。
- 陣的長相**無法**被作者微調：不滿意就得改魔法本身。這是 D1 的刻意取捨，不是缺陷。
- 兩個範例陣的 golden 重錄了一次；未來任何再度改動陣形幾何都要重付這筆，且豁免邊界不得擴張到 Casting。
- `sigilBudget = 1536` 只涵蓋 plan（筆畫＋形狀預覽）；節點與中心沿用 0006 的結構常數（≤ 64 粒）在其外。0012 抬高 `budgetCap` 之後的重新配額列於 func-spec 0016 §8-6。
- 陣形旋轉／動態陣形（0006 §9 已記帳）仍未做；`skPhase` 已在資料裡，加時間項即可，是下一輪最划算的一項。
