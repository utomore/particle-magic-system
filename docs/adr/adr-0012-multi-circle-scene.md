# ADR-0012：多陣合成的代數與場景層配額——`Monoid CompiledSpell`、逐界標 max、先到先得

- 狀態：已採納（2026-08-15）
- 相關：[architecture.md §6](../arch/architecture.md)（Init.md 參數對照表「多個效果疊」列）、§8.1（預算閘門）、§8.4（多法術並行）；ADR-0002（三層 DSL）、ADR-0004（dataflow，非 ECS）、ADR-0006（SoA 與 1 萬–10 萬粒目標）、ADR-0010（力場層組合點）、ADR-0011（C ABI 邊界）；落地 spec：[0012](../spec/func-0012-multi-circle-composition.md)

## 背景

Init.md 的參數對照表列了 11 種玩家可組合的語意，spec 0001–0011 落地了 10 種。剩下的一種是**「多個效果疊」**：玩家把兩張以上的魔法陣疊在一起，得到一個效果。它一直沒落地，不是因為難，而是因為它問的是一個**代數問題**而非功能問題——兩個已編譯的法術「加起來」是什麼意思？在四個生命週期界標、一份粒子預算、一串力場、一個 blend mode 都各有語意的情況下，這個「加」必須對每一個欄位分別給出答案，而且答案必須湊得成結合律，否則「疊三張陣」就會依賴玩家疊的順序括號怎麼放。

同時到期的是第二件事：粒子上限 `budgetCap` 從 spec 0002 起就是 **4096**——一個骨架期渲染器的護欄，不是效能設計。spec 0010 把熱路徑重寫完、量到 65 ns/粒之後，這個數字擋住的已經不是渲染器而是玩家。spec 0011 為此鋪好了管道（header 常數永釘 ＋ 查詢鏡射律），本輪是第一次真的走它。

兩件事同一輪，是因為它們互相需要：合成讓超過 4096 粒變得容易，而提升上限讓合成有意義。

## 決策

**D1（合成的代數形式：`CompiledSpell` 是 `Semigroup`／`Monoid`）** 多陣合成不引入新型別、不引入新的解釋器步驟，而是讓**編譯產物本身成為幺半群**。`compileMany :: [Circle] -> Either CompileError CompiledSpell` = 逐張編譯 → `mconcat` → 總預算檢查。理由：`CompiledSpell` 的每個欄位本來就是「一份可疊加的資料」（發射器是清單、預算是數字、場是清單），合成是這個結構的自然運算而不是加在它上面的機制；而選 `Monoid` 而非隨手寫一個 `merge` 函數，是為了讓**結合律成為型別類別的義務**、可以用 QuickCheck 逐位元守護，而不是靠註解宣稱。空清單合成為 `mempty`，於是「零張陣」也有定義，不必在呼叫端特判。

**D2（生命週期合併律：逐界標取 max）** `PhasePlan` 的四個界標（`ppDrawEnd`／`ppConvergeEnd`／`ppCastingEnd`／`ppEnd`）**各自取兩者最大值**，`spellLifetime` 跟著 `ppEnd`。

不變量保持的論證：`max` 對每個引數單調，故 `a₁≤a₂≤a₃≤a₄` 且 `b₁≤b₂≤b₃≤b₄` ⇒ `max a₁ b₁ ≤ max a₂ b₂ ≤ max a₃ b₃ ≤ max a₄ b₄`。語意直覺：合成陣的每個階段持續到**最慢的成分陣**結束；快的成分在自己的 envelope 內自然消退，沒有任何一方被截斷。

**D3（預算：相加，且對同一個上限檢查，錯誤型別不變）** 合成後的預算是各成分之和（`budgetPerEmitter` 串接、`budgetTotal` 相加），並對**同一個 `budgetCap`** 檢查——合成不是提高上限的手段。超額回既有的 `BudgetExceeded 合成總需求 上限`，不新增建構子：呼叫端的補救措施（少疊一張、或把 power 調小）與單陣超額時完全相同，多一個建構子只會多一條要處理的分支。

**D4（場的作用域：合成＝完全融合）** `spellFields` 串接後，**每個成分的力場作用於整個合成法術的 Casting 相位粒子**，包括別的成分帶來的粒子。這是語意選擇而非實作副產物：玩家把重力井和火環疊在一起，要的就是火被吸過去。技術上這條之所以「免費」成立，是因為 0007 的場輸入以 `emPhase == Casting` **過濾**而非以索引選擇——「發射器 0 是 casting 發射器」自 spec 0006 起就明文是**建構慣例而非讀取假設**，本輪是第一次有東西真的去踩它（第二張陣的 casting 發射器落在向量中間），而它站住了。

**D5（blend mode：串接序的第一個）** 合成法術仍然渲染成**一個 batch**，其 blend mode 取第一個發射器的——即第一張陣的。這不是新規則，是 architecture §10「一個法術一種混合模式」套用到合成的直接後果。可觀察的代價：把火（additive）與水（alpha）疊起來，整體以第一張陣的模式繪製。**記帳**：真正的修法是讓 `observeSpell` 依 blend 分批輸出多個 `RenderBatch`（`FrameOutput` 的型別已經允許），但那會改變 `pm_observe` 的 batch 描述陣列在既有宿主眼中的行為，屬對外合約演進，留給視覺輪連同貼圖／拖尾一起設計。

**D6（場景層：純值＋先到先得配額）** `Magic.Scene` 是 `Magic.Interface` 之上的**組合層**，不下探、不新增法術語意：`Scene` 是純值（`[(SpellId, ActiveSpell)]` 升冪 ＋ 全域上限），`advanceScene` = `map advanceSpell` ＋ `filter (not . isFinished)`，`observeScene` = batch 串接。無 IO、無鎖——多法術的執行緒策略仍屬宿主（0009 §9-2 立場不變）。

配額政策 v1 = **先到先得**：`castInto` 在「已用 ＋ 本次編譯預算 ≤ 全域上限」時受理，否則以 `QuotaExceeded 需求 剩餘` 拒收，且**場景一個位元都不變**。已用量由現存法術**即時求和**得出，不另立計數器——於是「法術結束時釋放配額」不是一個要記得做的動作，而是它不再被算進總和的必然結果；兩本帳不可能對不起來，因為只有一本。

**D7（上限值：4096 → 16384，由量測選定）** 選值規則：**單幀純 CPU（取樣＋quad 展開）≤ 2 ms 的最大 2 的冪**。2 ms ＝ 60 fps 幀預算的八分之一，其餘留給宿主的遊戲邏輯——這是庫的自制，不是它能跑多快。同機實測（func-spec 0012 §9.2）：4096 → 0.33 ms、8192 → 0.72 ms、**16384 → 1.45 ms**、32768 → 2.87 ms，故 16384。

同步義務：`Magic.Compile.budgetCap` 與 `src/ffi/Magic/FFI.hs` 的 `pmMaxParticles` 兩處，`include/particle_magic.h` 的 `PM_MAX_PARTICLES` **一字不動**（ADR-0011 D7「只加不改」＋ func-spec 0011 §9.4 的查詢鏡射律）。demo 的 `gpuCapacity` 自此**不再是這個常數的複本**，而是一個獨立的 GPU 上傳粒度（`Word16` 索引緩衝的上限使然）：超量 batch 改為分塊多次繪製。三份重複常數（ADR-0011 §後果所記的帳）自此降為兩份，且第三份是**查詢**而非複本。

**D8（場景層 v1 不上 C ABI）** `pm_scene_*` 不在本輪。理由是次序：場景層的 API 形狀應該先在 Haskell 面用過一輪、被實際宿主意見修過，再凍結成 C 合約——ADR-0011 D7 的「交付後只加不改」讓 C 面的錯誤比 Haskell 面的貴得多。非 Haskell 宿主在此之前仍可持有多個 `PmSpell*` 自行記帳（配額邏輯是十行加法）。

## 被否決的方案

**合併律**
- **取 min**：合成陣的階段在最快的成分結束時截斷。否決：破壞成分語意——玩家疊上去的第二張陣會被第一張陣砍掉尾巴，而他沒有做任何要求這件事發生的操作。
- **界標相加**：無物理意義（兩個 1.2 秒的繪陣期不會變成 2.4 秒的繪陣期），且 `ppEnd` 會隨疊的張數線性膨脹。
- **保留雙 plan（合成產物帶多份 `PhasePlan`）**：`PhasePlan` 是 spec 0006 交付即凍結的永久型別，改它的基數會漣漪到 `phaseAt`、Codec、以及每一個讀 `spellPhases` 的下游。而它換來的表達力（每個成分各自的階段時鐘）目前沒有任何需求。

**場的作用域**
- **隔離合成（per-emitter 場路由）**：各陣的場只作用於各陣自己的發射器。需要在 `FieldState` 的槽位身分之外再帶一層「這個發射器屬於哪個成分」的路由表，而那是 ADR-0010 D2 刻意壓平掉的東西。否決理由不是做不到，是**沒有需求且與直覺相反**（見 D4）。若日後出現需求（例如「反魔法陣」要抵銷而非疊加），此處是它的入口。

**配額政策**
- **按 power 加權／優先權搶佔**：讓大法術踢掉小法術。需要一個「重要性」的概念，而那是遊戲設計的詞彙不是粒子系統的——庫給的應該是拒收與剩餘量，讓宿主自己決定要不要先 `dismiss` 什麼。
- **每張陣獨立配額（合成不檢查總量）**：等於用合成繞過上限，把 D3 變成裝飾。
- **超額時自動縮減粒子數**：`emCount` 是編譯期常數，動態縮減會讓同一張陣在不同場景狀態下產生不同輸出——直接違反決定論（ADR-0007 的引用透明要求）。

**上限值**
- **維持 4096**：本輪的另一半（合成）會立刻撞到它——兩張 2048 粒的陣就滿了。
- **32768 或 65536**（0010 §9.2 的初步建議區間）：以本輪的直接量測（含 quad 展開，0010 的建議只算了取樣）分別是 2.87 ms 與 ~5.7 ms，超出 D7 的自制線。0010 的建議不是錯的，是它量的是取樣而非整幀。
- **讓上限可由宿主設定**：`budgetCap` 進入 `CastContext` 或全域設定。否決：同一張陣在不同宿主設定下會編譯成功或失敗，而 JSON 檔的可攜性（ADR-0005 的核心賣點）就是靠「一份 JSON 到哪都一樣」——把上限變成環境變數等於把它交出去。

## 後果

**正面**
- Init.md 參數對照表**最後一列落地**：11 列全部從宣稱變成測試守護的事實（架構論證維度的最後 15%）。
- 合成的正確性是**代數律**而非案例：結合律、單位律、疊加律（合成的取樣輸出 ≡ 成分取樣輸出的串接，逐位元）都是 property，新增的 `FaceShape`／`ForceField`／符文不會讓它們過期。
- 上限提升**沒有動到任何對外合約**：header 零字元變更、既有宿主零重編譯、10 個範例陣的 240 幀 golden 逐位元不變——ADR-0011 D7 的「只加不改」＋查詢鏡射律第一次被實際事件檢驗，而它撐住了。
- 場景層是**十幾行的純函數**，因為它上面沒有新語意可加——這件事本身是 ADR-0004（dataflow、非 ECS）的一個遲來的證據：多實體共存在這個架構裡不需要 entity manager。

**負面／記帳**
- **D5 的 blend 取捨是可觀察的**：疊火與水，第二張陣的混合模式被忽略。記在視覺輪帳上（見 D5）。
- **`gpuCapacity` 與 `budgetCap` 脫鉤後，demo 的 draw call 數變成 `⌈粒子數 / 4096⌉`**：16384 粒的法術要 4 次 draw call。仍與粒子數次線性，且 ADR-0009 的動態 mesh 路徑不變，但它不再是「永遠一次」。
- **場景層無 C ABI（D8）**：非 Haskell 宿主要自己記帳。記在 roadmap §3.3。
- **16384 粒的單陣在 60 fps 下佔 1.45 ms（8.7%）**：這是**設計上的上限而非典型值**，範例陣最密者仍在數百粒。若日後 Expr bytecode（architecture §8.2）或多執行緒取樣落地，這個常數應重新以同一條規則量測、而非隨手調高。
