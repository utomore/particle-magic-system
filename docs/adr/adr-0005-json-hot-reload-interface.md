# ADR-0005：JSON（Aeson）＋熱重載作為系統輸入介面

- 狀態：已採納（2026-08-11）
- 相關：[architecture.md §5.1](../architecture.md)

## 背景

POC 階段魔法陣的定義需要一個輸入管道。長期目標是玩家在遊戲內自由組合，但第一階段需要在「啟動速度」與「介面化程度」之間取捨。系統設計目標明確要求「系統輸入：要求格式」與「完美的介面化」。

## 決策

魔法陣以 **JSON 檔案**定義（Aeson 編解碼，含 `version` 欄位），外殼層監看檔案變更並**熱重載**（重載＝該魔法重新施法，狀態歸零）。數學式在 JSON 中為文字，由邊界層剖析為 `Expr` AST。

## 後果

**正面**：
- 系統輸入格式從第一天就是被強制定義、被每次執行驗證的**對外合約**，而非事後補寫的文件。
- 調參數改式子不需重新編譯 Haskell（h-raylib 專案編譯不快，這點價值很大），設計迭代循環縮到秒級。
- JSON 檔案就是未來遊戲內編輯器的存檔格式——編輯器只是這個格式的另一個生產者，管線不變。
- Aeson 是 Haskell 生態最成熟的序列化方案，泛型導出降低樣板。

**負面**：
- JSON 對人手寫不算友善（無註解、逗號規則嚴格）；錯誤訊息品質需要投入（剖析錯誤要帶位置）。
- 熱重載引入唯一一個「檔案系統」效果與跨平台檔案監看的細節（Windows 的 ReadDirectoryChangesW 語意、編輯器原子改名等），封裝在 `App.HotReload`。
- schema 演進需要紀律：`version` 欄位＋保留舊版解碼器＋`migrate` 函數，是持續性成本。

## 被否決的替代方案

- **程式內建範例**：啟動最快，但輸入格式介面化被無限期推遲，且每次調整都要重編譯——與「玩家組合魔法」的方向背道而馳。
- **遊戲內編輯器**：最貼近終極玩法，但 UI 工作量會吞掉 POC 的核心驗證時間；且在資料格式穩定前做編輯器必然返工。編輯器留待核心驗證後，屆時消費同一個 JSON 格式。
- **Dhall / YAML / 自訂 DSL 檔**：Dhall 有型別與註解很誘人，但生態小、玩家門檻高；YAML 的隱性轉型是出名的坑；自訂格式＝自己養一個剖析器與規格。JSON＋Aeson 是綜合成本最低的選擇，且未來由編輯器產生後「人寫 JSON」的缺點自然消失。
