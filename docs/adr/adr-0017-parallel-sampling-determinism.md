# ADR-0017：平行取樣的決定論，與核心依賴白名單的第一次擴充

- 狀態：已採納（2026-08-16）
- 相關：[architecture.md §7](../architecture.md)（GHC 設定與吞吐目標）、§8.2（Expr 加速三階梯）、§9.4（GC 停頓）；ADR-0006（SoA 與 1 萬–10 萬粒目標）、**ADR-0007（核心零 IO、簽名中無 `Eff`）**、ADR-0010（力場層的槽位身分）、ADR-0012 §後果（「若日後 Expr bytecode 或多執行緒取樣落地，`budgetCap` 應重新以同一條規則量測」）；落地 spec：[0022](../spec/func-0022-perf-second-tier.md)

## 背景

spec 0010 把單執行緒能做的都做完了：count-then-fill、時間窗剪枝、力場 SoA、in-place introsort，取樣常數因子從 161 降到 65 ns/粒。ADR-0012 D7 據此把 `budgetCap` 從 4096 抬到 16384，並在 §後果留下一筆帳：再往上抬，需要的是**庫本身更快**，而剩下的路只有兩條——每粒子做更少的事，或同時做更多粒子。

第二條路要求核心跑多執行緒。而 ADR-0007 說核心零 IO、簽名中不得出現 `Eff`。這兩件事看起來衝突，實際上不衝突，但**衝突與否完全取決於選哪一個平行機制**——這就是本 ADR 要裁決的事。

順帶要裁決的是它的代價：核心依賴白名單自 spec 0001 起是 `{base, vector, deepseq}`，三年沒動過（以本專案的輪次計）。任何平行機制都要動它。

## 決策

**D1（機制：`Control.Parallel.Strategies`，因為它是純的）** 平行取樣以 `parallel` 套件的 Strategies 實作，不用 `forkIO`／`MVar`／`unsafePerformIO`。

理由不是效能而是型別。`using :: a -> Strategy a -> a` 與 `Strategy a = a -> Eval a` 的形狀本身就說明了它只選擇**求值順序**、不改變**求值結果**：`x \`using\` s` 與 `x` 是同一個值。於是 `sample :: CompiledSpell -> CastContext -> Time -> ParticleBuffer` 的簽名一個字都不用改，ADR-0007 的「核心零 IO」不是被繞過而是**根本沒有被觸碰**。

`unsafePerformIO + forkIO` 能做到同樣的事，代價是核心裡出現一個說謊的型別：一個宣稱自己是純函數、實際上開執行緒的東西。那條路上，決定論要靠人工論證來守；這條路上，一半由型別免費守住。

**D2（切分方式：逐發射器再逐索引分片，因為邊界是純資料）** 平行的單位是 **shard**：某一個發射器的一段連續輸出列，至多 `parallelChunk` 列。分片絕不跨發射器。

決定論由切分方式**結構性成立**，不靠測試碰運氣：

1. **邊界是純資料**——發射器順序是 `spellEmitters` 的固定順序；存活索引區間由 `aliveRanges`（0010 S3）以 `O(log n)` 決定；分塊是對它們的一次固定算術走訪。三者都看不見執行緒、核心數或排程。
2. **分片彼此獨立**——粒子位置只依賴 `(CastContext, Time, EmitterSpec, 索引)`，這是解析式模型的根本性質（architecture §1.3）。沒有分片讀另一個分片的輸出。
3. **無跨執行緒歸約**——分片結果只**串接**，不相加、不求和、不排序合併。浮點加法的不可結合性因此沒有進入的縫隙。
4. **串接順序固定**——是分片清單的順序（發射器序、索引升冪），與完成順序無關。

四點合起來即**律 2**：任何執行緒數、任何排程，六欄輸出的位元模式相同。`test/ParallelSampleSpec.hs` 測的是這個推論的見證（含 `-N1`／`-N2`／`-N4` 三種核心數同輸出），以及四個前提各自的性質。

**逐發射器之外還逐索引分片**，是 spec 0022 §2.4 原文（「逐發射器切分」）的一個細化，理由是量測：一張用滿預算的陣通常只有個位數發射器，只按發射器切在 `budgetCap` 這個尺度上等於沒切。§2.4 的四點論證對索引區間逐字成立——它本來就是用「索引區間」寫的——所以這是同一個證明的更細用法，不是新的風險。

**D3（核心白名單擴充：`{base, vector, deepseq}` → `{base, vector, deepseq, parallel}`）** 本專案第一次擴充核心依賴白名單。`parallel` 自身只依賴 `base`／`array`／`containers`／`deepseq`——`deepseq` 已在白名單內，另外兩個是 GHC 隨附的 boot 套件，不引入任何第三方傳遞依賴。

白名單的意義從來不是「少裝東西」，而是「核心不得取得它不該有的能力」。`parallel` 通過這一關的理由與 D1 相同，而且這一輪把它從一句話變成一條測試：`test/BoundarySpec.hs` 除了比對白名單，還掃描 `src/core` 與 `src/boundary` 的全部原始碼（先剝註解），斷言其中沒有任何 `IO` 或 `Eff` 記號——並以殼層（`app/`、`src/ffi/`）確實掃得到兩者作為非空證明。一個會把效果帶進核心的依賴，從此不必等人在 review 裡發現。

**D4（閾值：8192 列，由實測選定；它只選路徑，不選答案）** 粒子數低於 `parallelThreshold = 8192` 時走 0010 的單趟填充路徑，之上走分片路徑。`parallelChunk = 1024` 列。

閾值不影響律 2——兩條路徑的輸出逐位元相同，閾值只決定跑哪一條，跨越閾值的那一幀不會閃爍。選值規則比照 ADR-0012 D7 的形狀（「由量測而非品味選定」）：**在所有量測到的核心數上都確實變快的最小 2 的冪**。同機實測（func-spec 0022 §9，AMD Ryzen 7 9800X3D，8 核 16 執行緒）：

| 粒子數 | -N1 | -N2 | -N4 | -N8 | -N16 |
|---|---|---|---|---|---|
| 4096 | 0.91× | 0.98× | 1.06× | 1.08× | 1.06× |
| **8192** | 0.93× | **1.06×** | **1.16×** | **1.36×** | **1.40×** |
| 16384 | 0.91× | 1.43× | 1.45× | 1.51× | 1.47× |
| 100000 | 0.87× | 1.44× | 2.54× | 3.45× | 3.90× |

4096 在 -N2 仍是虧的，8192 起全面轉正，故取 8192。`parallelChunk` 也是量出來的：同機 -N8、16384 粒，chunk 512／1024／4096 分別為 1.54×／1.45×／1.24×——4096 明顯太粗（分片太少，負載不均），512 與 1024 在雜訊內，取 1024。

**8192 低於 `budgetCap`（16384）**，所以這不是一個等待未來的機制：今天一張用滿預算的陣就會走上平行路徑，並在雙核以上實測快 1.4–1.5 倍。

**D5（本輪不改 `budgetCap`）** ADR-0012 §後果指名的兩件前提（Expr bytecode、多執行緒取樣）到本輪都已到位，但上限本身不動。理由是分工而非保守：改它要依 ADR-0012 D7 的同一條規則（「單幀純 CPU ≤ 2 ms 的最大 2 的冪」）重新量測，並同步 `src/ffi/Magic/FFI.hs` 的 `pmMaxParticles`——那是另一個 spec 的檔案。本輪只交量測，比照 0010 → 0012 的先例。

**D6（力場層不平行化）** `Field.step` 是跨幀狀態轉移，平行化要處理槽位寫入的順序性；而 0010 §9.2 量到帶場成本約 38 ns／槽·步、零場路徑實質免費。收益不明而風險高於取樣層，另輪。

**D7（量測平行加速必須用牆鐘，不能用 `tasty-bench`）** 這條寫進 ADR 而不只是註解，因為它已經騙過一次人。`tasty-bench` 量的是 **CPU 時間**，對平行計算而言那個數字會隨核心數**上升**——本輪驗收的初稿據此讀出「100k 粒平行慢 15%」，而同一份工作在牆鐘上快 3.45 倍。`bench/Bench.hs` 的平行段因此不走 `tasty-bench`，改用 `GHC.Clock.getMonotonicTime` 自帶的計時器，並在原始碼與 `PerfGoldenSpec` 兩處釘住這件事；其餘所有單執行緒量測仍用 `tasty-bench`，那裡它是對的工具。

## 被否決的方案

- **`unsafePerformIO` + `forkIO`**：核心會出現一個謊言型別（宣稱純、實際開執行緒），且決定論要靠人工論證而非型別守住。見 D1。
- **`async`／`stm`**：要的是決定論的**平行**（parallelism），不是**並行**（concurrency）。兩者都把排程與同步帶進核心，換來的表達力本輪一項都用不到。
- **把平行放在殼層（`App.Loop`）或宿主端**：不幫助 FFI 宿主（roadmap 維度 B）——它們拿到的是 `pm_observe` 的六欄，而那六欄是庫算出來的。抬高 `budgetCap` 需要的是庫本身更快。
- **GPU compute／transform feedback**：architecture §7 的永久非目標。
- **不設閾值，全部走平行路徑**：實測在 4096 列以下平行一律較慢（0.87–0.98×）。一個「小魔法變慢、大魔法變快」的取捨，在 8192 這一刀之後兩邊都不必付。
- **把 `Motion` 的 `Expr` 欄位換成 `ExprCode`**（spec 0022 §3 的原始草案）：否決，見 func-spec 0022 §10-1。`emitterBounds` 需要 AST 做區間算術，而 `Magic.Rune.Trajectory` 自帶 `ExprV3` 且本輪明文不碰 `Rune.hs`。bytecode 是**取樣器**要的東西，AST 是**編譯器**要的東西，兩份都留才是誠實的形狀。

## 後果

- 核心自此是多執行緒的，但**簽名上看不出來**——這正是 D1 想要的：`sample` 對呼叫端而言仍是一個時間的純函數。宿主不需要做任何事，也不能做任何事來改變結果。
- 需要 `-threaded` 才有實際加速。demo exe、`magic-validate`、test-suite 與 bench 都已帶上 `-threaded -rtsopts "-with-rtsopts=-N"`。**foreign library 沒有**：`.so`／`.dll` 的 RTS 由宿主的 `hs_init` 啟動，能力數是宿主的決定而非本庫的——這筆帳留給 C ABI 輪（func-spec 0018）決定要不要在 `cbits/pm_init.c` 裡表態。
- 平行路徑比單執行緒路徑多一趟 memcpy（分片各自產出後串接）。實測代價：-N1 時全面 0.87–0.93×，即約 7–13%。這正是閾值存在的理由，也是它被量出來而非猜出來的理由。
- 取樣器每粒子配置約 460 位元組（位置公式的十餘個中介 `V3`），這是本輪量測過程中浮現、**尚未處理**的一筆帳。平行加速在 -N8 之後趨緩（3.45× → 3.90×）與此有關。若日後要再抬 `budgetCap`，去掉這些中介的收益可能大於再加核心。記入 roadmap。
