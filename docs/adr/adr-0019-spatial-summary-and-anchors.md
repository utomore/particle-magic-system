# ADR-0019：空間摘要是系統的第三種輸出，發動點是形狀而非強度

- 狀態：已採納（2026-08-16）
- 相關：[architecture.md §7（發射器層級剔除、「明確不做」的空間分割結構）、§4.7（`RenderBatch` 是唯一輸出格式）、§11（粒子對粒子互動為永久非目標）](../architecture.md)；ADR-0003（槽位固定職責）、ADR-0006（SoA）、ADR-0007（核心零 IO、引用透明）、ADR-0008（核心無相機概念）、ADR-0011 D7（header only-add）、ADR-0012 D3（不得用合成繞過上限）；落地 spec：[func-0025](../spec/func-0025-spatial-output-anchors.md)

## 背景

系統至今對外只交兩種東西：`RenderBatch`（粒子）與錯誤。宿主拿得到「這些粒子長什麼樣」，拿不到「這道法術佔據哪裡」——想做碰撞、AoE 判定或視錐剔除，只有 `emitterBounds` 一個同半徑立方體，而且它**只在 Haskell 面**，C ABI 一個位元組都不給。

同時，`Anchor` 這個型別從 spec 0002 起就能表達任意位置與法線，陣形的節點發射器也一直在用；缺的只是「玩家沒有地方寫下它」。spec 0006 §9 把這件事記成待辦而非風險，正是因為它一直只是還沒接線。

本輪把兩件事一起做，而它們共用同一個要回答的問題：**系統可以對外說出什麼，而不改變自己是什麼。**

## 決策

### D1：空間摘要是 `RenderBatch` 的兄弟，不是 `FieldState` 的兄弟

architecture §7 把**空間分割結構**列在 POC 範圍外，§11 把**粒子對粒子互動**列為永久非目標。本 ADR 明文劃出界線，避免日後有人拿 func-spec 0025 當先例去做真正被禁止的事：

| | 被禁止的東西 | 本輪交付的東西 |
|---|---|---|
| 目的 | **模擬加速器**：讓粒子互相查詢鄰居 | **對外摘要**：讓宿主知道法術佔哪裡 |
| 方向 | 進入模擬迴圈，影響下一幀粒子狀態 | 從已算好的 buffer 讀出去，不影響任何粒子 |
| 狀態 | 需要跨幀維護的加速結構 | 純函數、零跨幀狀態、可隨時丟棄重算 |
| 複雜度 | 改變模型的複雜度等級 | O(粒子數) 單趟掃描 |
| 若移除 | 模擬壞掉 | 宿主少一個查詢，粒子輸出**逐位元相同** |

判準是**方向**：資訊只從模擬流出，永不流回。`test/Acceptance25Spec.hs` 與 `test/SpaceInterfaceSpec.hs` 把最後一列做成測試——呼叫任何空間查詢前後，`observeSpell` 的輸出逐位元相同。

**本 ADR 不為「粒子對粒子」開任何門**：那條線在 §7 與 §11 原地不動。真要做碰撞回饋（粒子反彈）需要把結果送回模擬，那會是輸出第一次影響輸入，屬於完全不同的一輪決策。

### D2：空間摘要是查詢，不是 `FrameOutput` 的欄位

`FrameOutput` **零變更**，摘要走獨立查詢（`spellBoundsOf`／`spellBoxOf`／`occupancyOf`／`occupancyMask`）。

兩個理由，第二個才是決定性的：

1. `FrameOutput` 加欄位會讓所有既有 pattern match 失效，是破壞性變更；
2. **絕大多數法術不需要它**。純視覺特效沒有碰撞需求，而格網每幀掃一次是實測 24 ns/粒（16384 粒 ≒ 0.40 ms，見 func-spec 0025 §8）——對用得到的人便宜，對用不到的人不該收錢。

這與 0007 零場結構性跳過、0015 opt-in 分批、0023 opt-in 速度欄是同一條紀律：**沒人用的東西不該有人付錢。**

### D3：`emitterBounds` 逐位元不動，貼合盒是新函數

新的分軸有向盒（`emitterBox`）更緊，實測各範例陣體積比 `emitterBounds` 的立方體小到 **1.5%–13%**（唯一例外是 `square-burst` 的 77%，因為 `radial-outward` 的行進軸逐粒子不同，三軸都得保守）。把 `emitterBounds` 直接改成回傳這個盒的世界 AABB 在數學上仍是合法上界，很誘人。

**否決。** `emitterBounds` 是 spec 0010 §9.3 的凍結匯出，外部 Haskell 宿主可能已依賴它的具體數值（例如以其體積做 LOD 判斷）。凍結的意義不是「語意不變」而是「**輸出不變**」——0015 的 `BillboardShape` 遷入核心、0012 的上限提升、0018 的 10 個場景匯出，全都走「加新的、不動舊的」。

守衛是 `test/golden/emitter-bounds-0025.txt`：在改動前的 build 上跑出來、提交進版控，`test/SpaceBoundsSpec.hs` 逐值比對。

### D4：格網的框由編譯期決定（可比較性律）

**框 = `spellBox` 在法術全生命週期的保守盒，整個法術生命週期固定。**

用當幀粒子的實際範圍切格子會更貼合，但格子的意義會**每幀都在變**：第 5 格在第 10 幀和第 11 幀指的是不同的空間，宿主既無法比較連續兩幀，也無法做「粒子進入某區域」的事件偵測。代價是法術早期粒子還沒擴散開時多數格子是空的——**那是正確的資訊，不是浪費**。

這條律決定了格網「可以拿來做什麼」，因此屬於架構層級而非實作細節。它也是 `spellBoxOf` 與 `emitterBoxOf` 取不同 horizon 的原因：前者答「這道法術會到哪」（整個生命週期，固定），後者答「這個發射器目前到哪」（當前年齡，逐幀成長）。因為盒對 horizon 單調成長，前者恆含後者。

### D5：N = 3 是預設維度，因為 27 恰好塞進一個 `Word32`

3³ = 27 ≤ 32，所以「哪些格子有粒子」在預設維度下是**一個 32 位元整數**：C 面一次查詢回一個 `uint32_t`，零配置、零緩衝管理，broad-phase 只要一次 `popcount` 或位元 AND。

而 27 這個數字不是巧合——它就是這個系統自己的九宮格（ADR-0003 的上下左右＋中心、`HollowSquare` 的口字型）沿法線擠出立體之後的格數，是 architecture §3.3「初始面沿法線擴充立體」在空間摘要上的自然離散化。N > 3 走 `pm_occupancy` 的計數陣列版本；N = 3 的遮罩是它的特例快路徑。

### D6：發動點不是符文，是陣級屬性

`anchors` 是 `phases`（0006）、`fields`（0007）之後的**第三個陣層級屬性**：不是符文槽、不佔用任何 ring、缺鍵或 `null` 等同「無」、既有檔逐位元照舊、schema 不升版。

它**不是符文**有語意理由：發動點是「這個法術從哪裡出來」，不是「這個法術是什麼」。ADR-0003 的四個槽位職責（核心＝本質、內圈＝行為、夾層＝調變、外圈＝展現）沒有一格在講位置——硬塞進外圈會污染「展現」的定義。

一個刻意的不對稱：**空陣列 `[]` 是錯誤，不是「無」的第三種寫法**。`[]` 到底是「沒有發動點」還是「用預設那個」，看檔案是猜不出來的；拒收它讓「無」的寫法維持兩種而不是三種。

### D7：能量等分，不是複製

N 個發動點時，粒子在發動點間**等分**（總量守恆），而非每點各拿一份完整的量。

理由：`essPower` 已經是決定能量的那個參數（architecture §6 步驟 1：「強度→能量預算」）。若加一個發動點就自動變兩倍強，玩家會發現**加發動點是繞過 `essPower` 的作弊路徑**，而 `budgetCap` 也會隨陣列大小線性膨脹、不再是任何東西的上界。等分讓「幾個發動點」是**形狀**的選擇而非**強度**的選擇——與 ADR-0012 D3 拒絕「用合成繞過上限」是同一個立場。

想要更強就調 `essPower`；那條路徑會照舊撞 `budgetCap`，如設計。

實作上餘數分給前面幾個發動點，因此各份相差至多 1 顆、總和**恰等於**單發動點時的值——`spellBudget` 一顆都沒變，這是可測的等式而非近似。

### D8：異質發動點不做，因為那已經是「多張陣」

「左手火、右手冰」不是本輪的 N 個發動點能表達的：它們共用同一份 fold 結果，只有位置與法線不同。異質發動點等於 N 張陣，而那是 `compileMany`／`castSpells` 已經做的事（各陣自帶 `anchors` 即可，`test/MultiAnchorSpec.hs` 有見證）。加第二套機制只會讓合成層與發動點層的職責重疊。

## 被否決的方案

| 方案 | 為什麼否決 |
|---|---|
| 把格網做成真正的空間分割並讓粒子查詢鄰居 | architecture §11 的永久非目標。會讓輸出影響輸入，改變模型的複雜度等級（D1） |
| 格網進 `FrameOutput` | 破壞性變更，且對絕大多數法術是白付的成本（D2） |
| 收緊 `emitterBounds` 本身 | 凍結匯出的輸出不得改變；宿主可能依賴其具體數值（D3） |
| 每幀依實際粒子分佈重算格網的框 | 格子的意義逐幀漂移，宿主無法比較兩幀，事件偵測不可能（D4） |
| 精確凸包／膠囊體／每幀貼合盒 | broad phase 的正確粒度是保守盒；精確幾何要每幀掃全部粒子求極值，且違反 D4 |
| 把 `anchors` 做成外圈符文 | 污染 ADR-0003 的槽位職責定義（D6） |
| 空陣列 `[]` 視同「無」 | 與缺鍵混淆，且兩種讀法都說得通，等於讓檔案有歧義（D6） |
| N 個發動點各拿完整粒子數 | 加發動點變成繞過 `essPower` 的作弊路徑，`budgetCap` 失去意義（D7） |
| 每個發動點各帶自己的符文 | 那就是多張陣，`compileMany` 已經做完了（D8） |
| 場景層的全場景聯集 `pm_scene_bounds` | 逐法術的 `pm_scene_spell_bounds` 已足夠，全場景聯集在宿主端是三行 |
| 視錐剔除本身進核心 | 核心沒有相機概念（ADR-0008）。核心交包絡，判定是宿主的事——architecture §7／spec 0010 §8-3 的分工不變 |

## 後果

**正面**

- 宿主第一次能回答「這道法術現在佔據哪裡」，而且非 Haskell 宿主與 Haskell 宿主**能力對等**（7 個純增補 C 匯出，`PM_ABI_VERSION` 仍為 1）。
- `OrientedBox`／`OccupancyGrid` 成為未來碰撞偵測、AoE 判定、視錐剔除的共同地基，語意與索引序交付即凍結。
- 主效果第一次可以有多個發動點，而這件事**沒有動到取樣器一行**——機制早就在 `Anchor` 裡，本輪只是接線。
- 既有 12 個範例陣、`test/golden/perf-0010/*` 的 8 個 golden **零重錄**。

**負面（記帳）**

- 空間摘要在粒子上限（16384）處是 **0.40 ms／次**，比 func-spec 0025 §2.2 估計的「幾十微秒」高一個數量級（典型法術的 256 粒仍只要 8 µs）。opt-in 的設計因此比當初預想的更重要，而不只是禮貌。若日後有宿主每幀都要，值得為 N = 3 做一條常數摺疊的特化路徑。
- `Anchor` 的宣告從 `Magic.Compile` 下移到 `Magic.Rune`（`Magic.Circle` 不能 import `Magic.Compile`）。匯出面一字未變（`Magic.Compile` 續行 re-export），但這是本專案第二次因為「某個型別變成玩家詞彙」而搬家——第一次是 spec 0015 的 `BillboardShape`。
- `Magic.Compile` 多匯出了一組**內部**的區間算術（`Interval`／`evalInterval`／…），只為了讓 `Magic.Space` 用**同一份**程式碼而不是第二份拷貝。這是刻意的代價：兩份區間算術會讓「新的更緊、舊的不變」變成兩個獨立的東西，而它們必須是同一個。
- 時間參數化的界（「此刻」而非「至此刻為止」）、anchor 的時變（發動點跟隨施法者）兩筆記帳留給後續，見 func-spec 0025 §7。
